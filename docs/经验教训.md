# 经验教训记录

> 目的：每完成一小步都验证；**失败必须回退并在此记录原因与规避方法**，防止再犯。
> 规则：只记录**真实发生过**的问题，不写假设性的。
> 每条格式：现象 → 根因 → 处置 → 规避（可执行的规则）。

## L-001 · PowerShell 脚本里的中文导致 ParserError

**发生阶段**：P0 建立验证闸口（`scripts/check.ps1`）

**现象**：
```
所在位置 scripts\check.ps1:80 字符: 22
+   Write-Host "[SKIP] L3 绔埌绔瘎娴嬶紙鏈寚瀹?-Full锛? -ForegroundColor ...
数组索引表达式丢失或无效。
```
脚本从未执行，直接解析失败。注意报错里中文已变成 `绔埌绔` 这类乱码。

**根因**（实测确认，非推测）：
| 检查项 | 值 |
|---|---|
| 文件前 4 字节 | `23 20 63 68`（即 `# ch`）→ **无 UTF-8 BOM** |
| PowerShell 版本 | **5.1.19041.6456 · Desktop** |
| 系统 ANSI 代码页 | **936 (GBK)** |

PowerShell **5.1**（Windows 内置版）读取**无 BOM** 的 `.ps1` 时，按**系统 ANSI 代码页**解码，
而不是 UTF-8。代码页是 936，于是 UTF-8 的中文字节被按 GBK 解成乱码；
乱码里恰好出现 `?` `（` 等在 PowerShell 语法中有意义的字符，就把字符串提前截断，
进而报"数组索引表达式丢失""字符串缺少终止符"等**看似与编码无关**的语法错误。

**这是一个"误导性极强的坑"**：报错信息指向语法/索引，真实原因是文件编码。

**备注**：本项目的《项目全景深度解析》第 7 条踩坑记录（`alembic.ini` 中文注释在 Windows 按 GBK 读崩）
**是同一个根因**。说明这个项目**已经踩过一次**，我这次又踩了——所以必须升级为强制约定。

**处置**：
把 `scripts/check.ps1` 重写为 **ASCII-only**（注释与输出全用英文），功能一字不减。

**规避（强制规则）**：
1. **`.ps1` / `.ini` / `.bat` 等由系统 shell 或第三方库解析的配置/脚本文件，一律 ASCII-only**，不写中文。
2. 中文只写在 **UTF-8 且被 Python/Node 读取**的文件里（`.py` / `.ts` / `.md` / `.json` / `.yaml`）——
   这些语言的读取器显式指定 UTF-8，不受代码页影响。
3. 若确实要在 `.ps1` 里写非 ASCII，**必须存成 UTF-8 with BOM**（`EF BB BF`）。
   但**首选 ASCII-only**，因为它对编码和工具链完全不敏感。
4. 新增 `.ps1` 后，**先 `Get-Content` 确认能正常解析**再执行；报"语法错误"时
   **第一反应检查编码而不是语法**。

**验证**：改写后 `.\scripts\check.ps1` 退出码 0，L1/L2 全通过。

## L-002 · PowerShell 5.1 把原生命令的 stderr 当"终止性错误"，导致闸口自杀

**发生阶段**：P0 首次运行 `.\scripts\check.ps1 -Full`

**现象**：
L1/L2 正常通过，但跑到 L3（`python -m eval`）时脚本整体中止：
```
>> L3a retrieval eval (retrieval-only)
python.exe : 2026-10-08 15:08:07,668 - INFO - [Eval] 初始化 RAG Pipeline...
    + CategoryInfo          : NotSpecified: (2026-10-08 15:0...:String) [], RemoteException
    + FullyQualifiedErrorId : NativeCommandError
[exit code: 1]
```
注意：**Python 根本没失败**，它只是把日志写到了 stderr。

**根因**：
脚本开头设了 `$ErrorActionPreference = "Stop"`。
Windows PowerShell 5.1（`Desktop` 版）会把**原生命令（native command）的 stderr 输出**
包装成 `ErrorRecord`。在 `Stop` 模式下，这个 `ErrorRecord` 会被当作**终止性错误**，
直接中断整个脚本——**即使被调用的命令实际执行成功（exit code 0）**。

本项目所有 Python 工具都用 `logging` 写 stderr（INFO 级进度日志），
所以这个组合会让闸口**必然自杀**，无法用于任何真实命令。

**这是第二个"报错信息误导人"的坑**：`RemoteException` / `NativeCommandError` 看起来像
Python 崩了，实际是 PowerShell 的错误处理策略问题。

**处置**：
1. `$ErrorActionPreference` 改为 **`Continue`**（原生命令的成败**只用 `$LASTEXITCODE` 判断**，
   这是官方推荐做法）。
2. 所有原生命令输出改为 `*>&1 | Out-String`，把 stderr 合并进正常流再处理。

**规避（强制规则）**：
1. **调用原生命令（python/docker/git/node…）的 `.ps1` 脚本，不要用 `$ErrorActionPreference = "Stop"`**。
   用 `Continue` + `$LASTEXITCODE` 判成败。
2. 需要收拢原生命令输出时用 `*>&1`（合并所有流），不要只用 `2>&1`。
3. 看到 `NativeCommandError` / `RemoteException` 时，**先怀疑错误处理策略，而不是被调命令**。

## L-003 · 在闸口的 scriptblock 里写 `exit 0` 会退出整个脚本

**发生阶段**：P0 同上（与 L-002 同一次修复中发现）

**现象**：
修完 L-002 后，`L3a` 显示 `[PASS]`，但 **L3b（回归比对）根本没执行**，
脚本直接跳到收尾并打印"全部通过"。

**根因**：
我为了忽略 `eval` 的非 0 退出码（有 1 道基线已知失败题），在 `Invoke-Gate` 传入的
scriptblock 里写了 `exit 0`。
但 **`exit` 作用于整个 PowerShell 会话/脚本进程，不是 scriptblock**——
所以它在 L3a 结束时就把整个 `check.ps1` 退出了。

**更危险的后果**：脚本"看起来通过了"，但**实际跳过了真正的回归比对**。
这属于**闸口假阳性**——比 L-002 的硬失败更危险，因为它会让人误以为改动是安全的。

**处置**：
scriptblock 内改为只重置退出码 `$global:LASTEXITCODE = 0`，并把它放进标准的
`Invoke-Gate` 里，让 `[PASS]`/`[FAIL]` 由统一的逻辑判定。

**规避（强制规则）**：
1. **`Invoke-*` 包装函数传入的 scriptblock 内，禁止使用 `exit`**（要用 `return`）。
   需要"忽略上一条命令的退出码"时，**重置 `$LASTEXITCODE` 而不是 `exit 0`**。
2. **闸口类脚本必须验证"它真的会跑完整流程"**：
   本次是靠人工逐行阅读输出才发现 L3b 被跳过。规则：
   **新增/修改闸口后，必须造一次"应当失败"的场景，确认闸口真的报 FAIL**——
   一个永远打印 PASS 的闸口比没有闸口更危险。
   （同样的原则已用在 `test_eval_compare.py`：用合成数据构造 4 类回归，断言闸口都能检出。）

**验证**：修复后 `.\scripts\check.ps1 -Full` 完整跑完 L1→L2→L3a→L3b，
末尾输出 `OK - all gates passed`，退出码 0；L3b 实际执行了 107 题逐题比对。

## L-004 · 误读 pg_hba.conf：Docker 端口映射下 `127.0.0.1 trust` 规则永不生效

**发生阶段**：P1.1 建 `kb_analytics` 库 + `kb_ro` 只读角色

**现象**：
建库、建角色、赋权都成功，但**宿主机以 `kb_ro` 连接失败**：
```
connection to server at "127.0.0.1", port 5432 failed: fe_sendauth: no password supplied
Multiple connection attempts failed. All failures were:
- host: 'localhost', port: 5432, hostaddr: '::1': ... no password supplied
- host: 'localhost', port: 5432, hostaddr: '127.0.0.1': ... no password supplied
```

**我的错误判断（第一次诊断）**：
我先查了 `pg_hba.conf`，看到这条就下结论"本地是 trust，不需要口令"，
于是在配置里把只读角色口令设计为"留空 = 不设口令"：
```
host    all             all             127.0.0.1/32            trust
```
**这个判断是错的。**

**根因**（实测确认）：
Docker 的端口发布（`ports: 5432:5432`）走 **NAT/masquerade**，不是简单的 socket 转发。
宿主机发往 `127.0.0.1:5432` 的连接，在容器网络命名空间里源地址被改写成
**网桥网关地址**（`172.x.x.x`），因此

- 它**永远匹配不到** `127.0.0.1/32` 那条 trust 规则；
- 最终落到 `pg_hba.conf` 末行的 `host all all all scram-sha-256`，**必须提供口令**。

**决定性的验证**：用 `rag` 账号从宿主机连也一样失败（`rag` 明明有口令 `rag`）。
如果是"没设口令"的问题，带口令的 `rag` 应该成功——它同样失败了，
说明**是认证方式不匹配，而不是口令本身**。

```powershell
# 宿主机（python/psycopg）：
FAIL host=127.0.0.1  user=kb_ro  -> fe_sendauth: no password supplied
FAIL host=127.0.0.1  user=rag    -> fe_sendauth: no password supplied   # 关键反证
# 容器内：
docker exec ... psql -U kb_ro -d kb_analytics   -> OK（走 local ... trust）
```

**PG 自己的视图也确认规则是生效的**（`pg_hba_file_rules` 里 `127.0.0.1/32 trust` 无 error），
所以问题不在配置文件，而在**匹配失败的地址改写**。

**处置**：
1. 只读角色**必须有口令**：`effective_ro_password()` = 配置值，否则用本地开发默认值。
2. 把权限自检**拆成两条独立路径**，这样失败时能立刻定位是"认证"还是"权限"问题：
   - **A. 宿主机连接**（走 scram）→ 验证口令配置正确
   - **B. 容器内连接**（走 local trust）→ 验证**权限本身**正确，绕开口令变量
   两条都过才算通过。
3. `.env.example` 补 `ANALYTICS_RO_PASSWORD`，并注明"留空则用本地开发默认值，
   生产必须注入强口令"。

**规避（强制规则）**：
1. **不要从 `pg_hba.conf` 的字面内容推断"本地免密"**。
   在 Docker 部署里，**宿主机连接一律按 scram 处理，必须提供口令**。
   判断依据应该是**实测**（`psql`/`psycopg` 真的连一次），而不是读配置。
2. 排查"连接被拒"类问题时，**必须用一个已知正确的账号做对照实验**。
   本次正是靠 `rag`（有口令）也失败，才排除了"只读角色没设口令"这个错误方向。
3. 权限验证要**区分"认证"与"授权"两个维度**并分别给结论——
   混在一起报"连接失败"会掩盖真正的病因。
