## L-001 · PowerShell 脚本里的中文导致 ParserError

**发生阶段**：P0 建立验证闸口（`scripts/check.ps1`）

**现象**：
```
所在位置 scripts\check.ps1:80 字符: 22
+   Write-Host "[SKIP] L3 绔埌绔瘎娴嬶紙鏈寚瀹?-Full锛? -ForegroundColor ...
数组索引表达式丢失或无效。
```
脚本从未执行，直接解析失败。注意报错里中文已变成 `绔埌绔` 这类乱码。

**根因**（实测确认，非推测）：
| 检查项 | 值 |
|---|---|
| 文件前 4 字节 | `23 20 63 68`（即 `# ch`）→ **无 UTF-8 BOM** |
| PowerShell 版本 | **5.1.19041.6456 · Desktop** |
| 系统 ANSI 代码页 | **936 (GBK)** |

PowerShell **5.1**（Windows 内置版）读取**无 BOM** 的 `.ps1` 时，按**系统 ANSI 代码页**解码，
而不是 UTF-8。代码页是 936，于是 UTF-8 的中文字节被按 GBK 解成乱码；
乱码里恰好出现 `?` `（` 等在 PowerShell 语法中有意义的字符，就把字符串提前截断，
进而报"数组索引表达式丢失""字符串缺少终止符"等**看似与编码无关**的语法错误。

**这是一个"误导性极强的坑"**：报错信息指向语法/索引，真实原因是文件编码。

**备注**：本项目的《项目全景深度解析》第 7 条踩坑记录（`alembic.ini` 中文注释在 Windows 按 GBK 读崩）
**是同一个根因**。说明这个项目**已经踩过一次**，我这次又踩了——所以必须升级为强制约定。

**处置**：
把 `scripts/check.ps1` 重写为 **ASCII-only**（注释与输出全用英文），功能一字不减。

**规避（强制规则）**：
1. **`.ps1` / `.ini` / `.bat` 等由系统 shell 或第三方库解析的配置/脚本文件，一律 ASCII-only**，不写中文。
2. 中文只写在 **UTF-8 且被 Python/Node 读取**的文件里（`.py` / `.ts` / `.md` / `.json` / `.yaml`）——
   这些语言的读取器显式指定 UTF-8，不受代码页影响。
3. 若确实要在 `.ps1` 里写非 ASCII，**必须存成 UTF-8 with BOM**（`EF BB BF`）。
   但**首选 ASCII-only**，因为它对编码和工具链完全不敏感。
4. 新增 `.ps1` 后，**先 `Get-Content` 确认能正常解析**再执行；报"语法错误"时
   **第一反应检查编码而不是语法**。

**验证**：改写后 `.\scripts\check.ps1` 退出码 0，L1/L2 全通过。

## L-002 · PowerShell 5.1 把原生命令的 stderr 当"终止性错误"，导致闸口自杀

**发生阶段**：P0 首次运行 `.\scripts\check.ps1 -Full`

**现象**：
L1/L2 正常通过，但跑到 L3（`python -m eval`）时脚本整体中止：
```
>> L3a retrieval eval (retrieval-only)
python.exe : 2026-10-08 15:08:07,668 - INFO - [Eval] 初始化 RAG Pipeline...
    + CategoryInfo          : NotSpecified: (2026-10-08 15:0...:String) [], RemoteException
    + FullyQualifiedErrorId : NativeCommandError
[exit code: 1]
```
注意：**Python 根本没失败**，它只是把日志写到了 stderr。

**根因**：
脚本开头设了 `$ErrorActionPreference = "Stop"`。
Windows PowerShell 5.1（`Desktop` 版）会把**原生命令（native command）的 stderr 输出**
包装成 `ErrorRecord`。在 `Stop` 模式下，这个 `ErrorRecord` 会被当作**终止性错误**，
直接中断整个脚本——**即使被调用的命令实际执行成功（exit code 0）**。

本项目所有 Python 工具都用 `logging` 写 stderr（INFO 级进度日志），
所以这个组合会让闸口**必然自杀**，无法用于任何真实命令。

**这是第二个"报错信息误导人"的坑**：`RemoteException` / `NativeCommandError` 看起来像
Python 崩了，实际是 PowerShell 的错误处理策略问题。

**处置**：
1. `$ErrorActionPreference` 改为 **`Continue`**（原生命令的成败**只用 `$LASTEXITCODE` 判断**，
   这是官方推荐做法）。
2. 所有原生命令输出改为 `*>&1 | Out-String`，把 stderr 合并进正常流再处理。

**规避（强制规则）**：
1. **调用原生命令（python/docker/git/node…）的 `.ps1` 脚本，不要用 `$ErrorActionPreference = "Stop"`**。
   用 `Continue` + `$LASTEXITCODE` 判成败。
2. 需要收拢原生命令输出时用 `*>&1`（合并所有流），不要只用 `2>&1`。
3. 看到 `NativeCommandError` / `RemoteException` 时，**先怀疑错误处理策略，而不是被调命令**。

## L-003 · 在闸口的 scriptblock 里写 `exit 0` 会退出整个脚本

**发生阶段**：P0 同上（与 L-002 同一次修复中发现）

**现象**：
修完 L-002 后，`L3a` 显示 `[PASS]`，但 **L3b（回归比对）根本没执行**，
脚本直接跳到收尾并打印"全部通过"。

**根因**：
我为了忽略 `eval` 的非 0 退出码（有 1 道基线已知失败题），在 `Invoke-Gate` 传入的
scriptblock 里写了 `exit 0`。
但 **`exit` 作用于整个 PowerShell 会话/脚本进程，不是 scriptblock**——
所以它在 L3a 结束时就把整个 `check.ps1` 退出了。

**更危险的后果**：脚本"看起来通过了"，但**实际跳过了真正的回归比对**。
这属于**闸口假阳性**——比 L-002 的硬失败更危险，因为它会让人误以为改动是安全的。

**处置**：
scriptblock 内改为只重置退出码 `$global:LASTEXITCODE = 0`，并把它放进标准的
`Invoke-Gate` 里，让 `[PASS]`/`[FAIL]` 由统一的逻辑判定。

**规避（强制规则）**：
1. **`Invoke-*` 包装函数传入的 scriptblock 内，禁止使用 `exit`**（要用 `return`）。
   需要"忽略上一条命令的退出码"时，**重置 `$LASTEXITCODE` 而不是 `exit 0`**。
2. **闸口类脚本必须验证"它真的会跑完整流程"**：
   本次是靠人工逐行阅读输出才发现 L3b 被跳过。规则：
   **新增/修改闸口后，必须造一次"应当失败"的场景，确认闸口真的报 FAIL**——
   一个永远打印 PASS 的闸口比没有闸口更危险。
   （同样的原则已用在 `test_eval_compare.py`：用合成数据构造 4 类回归，断言闸口都能检出。）

**验证**：修复后 `.\scripts\check.ps1 -Full` 完整跑完 L1→L2→L3a→L3b，
末尾输出 `OK - all gates passed`，退出码 0；L3b 实际执行了 107 题逐题比对。

## L-004 · 误读 pg_hba.conf：Docker 端口映射下 `127.0.0.1 trust` 规则永不生效

**发生阶段**：P1.1 建 `kb_analytics` 库 + `kb_ro` 只读角色

**现象**：
建库、建角色、赋权都成功，但**宿主机以 `kb_ro` 连接失败**：
```
connection to server at "127.0.0.1", port 5432 failed: fe_sendauth: no password supplied
Multiple connection attempts failed. All failures were:
- host: 'localhost', port: 5432, hostaddr: '::1': ... no password supplied
- host: 'localhost', port: 5432, hostaddr: '127.0.0.1': ... no password supplied
```

**我的错误判断（第一次诊断）**：
我先查了 `pg_hba.conf`，看到这条就下结论"本地是 trust，不需要口令"，
于是在配置里把只读角色口令设计为"留空 = 不设口令"：
```
host    all             all             127.0.0.1/32            trust
```
**这个判断是错的。**

**根因**（实测确认）：
Docker 的端口发布（`ports: 5432:5432`）走 **NAT/masquerade**，不是简单的 socket 转发。
宿主机发往 `127.0.0.1:5432` 的连接，在容器网络命名空间里源地址被改写成
**网桥网关地址**（`172.x.x.x`），因此

- 它**永远匹配不到** `127.0.0.1/32` 那条 trust 规则；
- 最终落到 `pg_hba.conf` 末行的 `host all all all scram-sha-256`，**必须提供口令**。

**决定性的验证**：用 `rag` 账号从宿主机连也一样失败（`rag` 明明有口令 `rag`）。
如果是"没设口令"的问题，带口令的 `rag` 应该成功——它同样失败了，
说明**是认证方式不匹配，而不是口令本身**。

```powershell
# 宿主机（python/psycopg）：
FAIL host=127.0.0.1  user=kb_ro  -> fe_sendauth: no password supplied
FAIL host=127.0.0.1  user=rag    -> fe_sendauth: no password supplied   # 关键反证
# 容器内：
docker exec ... psql -U kb_ro -d kb_analytics   -> OK（走 local ... trust）
```

**PG 自己的视图也确认规则是生效的**（`pg_hba_file_rules` 里 `127.0.0.1/32 trust` 无 error），
所以问题不在配置文件，而在**匹配失败的地址改写**。

**处置**：
1. 只读角色**必须有口令**：`effective_ro_password()` = 配置值，否则用本地开发默认值。
2. 把权限自检**拆成两条独立路径**，这样失败时能立刻定位是"认证"还是"权限"问题：
   - **A. 宿主机连接**（走 scram）→ 验证口令配置正确
   - **B. 容器内连接**（走 local trust）→ 验证**权限本身**正确，绕开口令变量
   两条都过才算通过。
3. `.env.example` 补 `ANALYTICS_RO_PASSWORD`，并注明"留空则用本地开发默认值，
   生产必须注入强口令"。

**规避（强制规则）**：
1. **不要从 `pg_hba.conf` 的字面内容推断"本地免密"**。
   在 Docker 部署里，**宿主机连接一律按 scram 处理，必须提供口令**。
   判断依据应该是**实测**（`psql`/`psycopg` 真的连一次），而不是读配置。
2. 排查"连接被拒"类问题时，**必须用一个已知正确的账号做对照实验**。
   本次正是靠 `rag`（有口令）也失败，才排除了"只读角色没设口令"这个错误方向。
3. 权限验证要**区分"认证"与"授权"两个维度**并分别给结论——
   混在一起报"连接失败"会掩盖真正的病因。

## L-005 · 把"文档里估的行数/列数"当成真值写进断言 → 断言本身是错的

**发生阶段**：P1.5 装载 `cost_data.xlsx` 并跑真值自检

**现象**：
ETL 完全成功（4 张表全部建出、表头陷阱正确跳过、10000 行员工表装载无误），
但真值自检报失败：
```
- [cost_data] SELECT count(*) FROM cost_data ... 期望 7 得到 6
- [cost_data] SELECT count(*) FROM information_schema.columns ... 期望 8 得到 9
```

**根因**（两个独立错误，都是"拿估计当真值"）：

**错误 1 —— 行数 7 vs 6。**
我在写改造方案文档时用的是 `pandas.read_excel` 的 `df.shape` 印象值，
没有核对 openpyxl 的原始行。实测 `cost_data.xlsx` 有 **8 个非空行**：
```
[0] 标题行  「橱柜项目成本明细表」        -> 被表头探测正确跳过
[1] 表头行  「项目/品牌型号/.../备注」
[2..6] 数据 5 行
[7] 尾部汇总脚注「汇总：铰链(28×20)、颗粒板…」  <-- 首列有值，openpyxl 视为数据行
```
=> 装载 **6 行**（含那条脚注），不是文档里写的 7。

**错误 2 —— 列数 8 vs 9。**
我在改断言时把注释写成"7 业务列 + tenant_id"，然后写了 `8`——
**连自己的注释都没算对**：实际是 **8 业务列**（col_1…col_8）+ tenant_id = **9**。
DDL 日志里其实已经明确打了「已重建表 cost_data（8 列）」，但我没去核对。

**这是最危险的一类错误**：代码是对的，断言是错的。
如果当时"顺着断言去改代码"（比如强行让表变成 7 列），就会**把正确的实现改坏**。

**处置**：
1. 用 openpyxl 打印 `cost_data.xlsx` 的**全部非空行**，逐行确认结构，据此修正断言为 6 行 / 9 列。
2. 在 `seed.py` 的 `TRUTH_CHECKS` 上方**写清真实行结构注释**（含 [0]/[1]/[2..6]/[7] 的逐行说明），
   并把"8 业务列 + tenant_id = 9"的算式写进注释，避免下次再算错。
3. 顺带记录了尾部脚注行的存在 —— 这是一个**已知的数据质量瑕疵**（脚注被当数据），
   不属于 bug（ETL 只做机械转换），但要在数据字典里可解释。

**规避（强制规则）**：
1. **断言里的期望值必须来自"实测"，不能来自文档、注释或记忆**。
   写断言前先跑一次查询把真实值打印出来，再把打印结果写进断言。
2. **断言失败时，第一反应是"怀疑断言"而不是"改代码"**。
   本次若直接改代码去迎合 7 行/8 列，会把正确实现改坏。
   正确顺序：打印真实数据 → 判断谁错 → 改错的那一方。
3. **文档里的数字要标注来源**。改造方案第三部分那些真值（1042/1010/32/192）
   是用 `pandas` 直读算出来的，可信；而"cost_data 7 行"是估计值，不可信。
   今后文档里区分标注「实测」与「估计」。
4. **代码已经打印的诊断信息要真的去看**。DDL 日志「cost_data（8 列）」早就说明了列数，
   看日志能省掉一轮试错。

## L-006 · PowerShell here-string 被提交信息里的引号提前终止

**发生阶段**：P1 提交（`git commit -m @'...'@`）

**现象**：
`git commit` 报出与提交内容毫不相干的错误：
```
error: pathspec 'transaction 拒绝

验证: check.ps1 -Full 全绿
...
经验教训: L-005 —— ...' did not match any file(s) known to git
```
提交**没有产生**，但 `git add` 已经生效 → 工作区处于"已暂存未提交"的中间态。

**根因**：
PowerShell 的 here-string 终止符 `'@` **必须位于行首**。
我的提交信息里有一行以 `拒绝` 结尾，紧接着的内容里出现了 `'@` 之外的引号组合，
更关键的是：信息中包含的英文单引号/中文引号与 here-string 边界发生冲突，
使 PowerShell 提前结束了字符串，把剩余内容当成 `git` 的额外参数（pathspec）。

**这类错误的特征**：报错信息指向 `pathspec`（文件路径），
但真实原因在 **shell 的字符串解析**——与 L-001/L-002 同属"报错信息误导人"家族。

**处置**：
改用 **`git commit -F <消息文件>`**：先把提交信息写入文件，再让 git 从文件读。
彻底绕开所有 shell 引号/换行/编码问题。
（提交后删除临时文件，避免污染仓库。）

**规避（强制规则）**：
1. **多行或含标点的提交信息，一律用 `-F` 从文件读**，不要用 `-m`/here-string。
   ```powershell
   # 推荐
   git commit -F .git\COMMIT_MSG_TMP.txt
   ```
2. here-string 若必须用，**终止符 `'@` 必须顶格写在行首**，
   且正文里避免出现可能与边界混淆的引号组合。
3. **`git add` 之后才发现提交失败时，不要慌**：暂存区仍在，
   直接补一次成功的 `git commit` 即可（本次即如此，无需重新 add）。

## 提交失败/中间态的处理约定

本次遇到"已 add、未 commit"的中间态，处理方式记录下来备查：
1. `git status --short` 确认暂存区内容仍在（首列为 `A`/`M`）；
2. **不要** `git reset`（会白丢已暂存的整理工作）；
3. 修正提交信息后直接 `git commit` 即可完成；
4. 确认 `git log --oneline -1` 出现新提交、`git status` 变干净，
   才算这一步真正闭合。

## L-007 · `sqlglot` 的"宽松解析"实测确证：裸 `SELECT` 被当成合法查询

**发生阶段**：P2.1 SQL 安全网关（`guard.py` 攻击载荷测试）

**现象**：
攻击载荷测试 93 例里 92 通过，唯一失败的是最不起眼的一条：
```
MUST_REJECT: ("SELECT", "残缺语句")
AssertionError: 漏放（安全事故）: [残缺语句] 'SELECT'
assert not True
  where True = GuardResult(ok=True,
      sql='SELECT * FROM (SELECT) AS _q LIMIT 200', ...).ok
```

**根因**：
`sqlglot.parse("SELECT")` **不报错**，而是解析成一个 `exp.Select` 节点 ——
只是它既没有投影列（`expressions` 为空）也没有 FROM 子句。
我的 guard 检查了"根节点是 Select"就放行，于是继续走 LIMIT 注入，
把无意义的 AST 包裹成了：
```sql
SELECT * FROM (SELECT) AS _q LIMIT 200
```
这**在 PostgreSQL 里是语法非法的**。也就是说，这个输入没被安全网关干净拒绝，
而是会"漏到数据库层再报错"。

**这正是 sqlglot 官方 FAQ 所说的情况**（本次是实测确证，不是照抄文档）：
> *"The parser is intentionally lenient, so it can accept queries that a real engine
> would reject. **SQLGlot is a transpiler, not a validator.**"*

**两条重要推论**：
1. **"解析成功" ≠ "语句合法"**。把 `parse()` 不抛异常当作合法性依据是错的。
   必须**额外做结构完整性检查**（本次补的是：既无投影列又无 FROM → 拒绝）。
2. 这从实测层面**验证了"四层防御"设计的必要性**：如果只有第一层，
   这类输入会穿过网关到达数据库。正因为下面还有只读事务、角色权限、RLS 三层，
   即便第一层漏了也不会造成实际损害。

**处置**：
在根节点检查之后新增 3b 结构完整性自检：
```python
has_projection = bool(tree.expressions)
has_from = tree.args.get("from") is not None or tree.find(exp.From) is not None
if not has_projection and not has_from:
    return GuardResult(False, "", "SELECT 结构不完整（无投影列且无 FROM 子句）",
                       "SQL 结构不完整：…请生成完整语句，例如 SELECT count(*) FROM employees。")
```

**规避（强制规则）**：
1. **不要用"解析器不报错"当作合法性判据**。解析器（尤其 sqlglot）以宽松为设计目标。
   安全的判据是"**结构符合预期**"，需要显式检查必需成分。
2. **安全校验要写成对抗测试**（本次 44 条 MUST_REJECT + 22 条 MUST_ALLOW）。
   本次这条 `SELECT` 载荷是"残缺输入"类的代表 ——
   这类**最不起眼的载荷往往就是漏网的那个**，因为它们不像攻击。
3. 新增安全规则时，**同时补一条 MUST_REJECT 用例**，否则规则会随时间腐化。

**验证**：修复后 `pytest tests/test_sql_guard.py` → **93 passed**

## L-008 · 用 asyncpg 连接串配 `create_engine()` → MissingGreenlet

**发生阶段**：P2.2 只读 SQL 执行器（首次真连 PostgreSQL）

**现象**：
```
sqlalchemy.exc.MissingGreenlet: greenlet_spawn has not been called;
can't call await_() here. Was IO attempted in an unexpected place?
sys:1: RuntimeWarning: coroutine 'connect' was never awaited
```

**根因**：
配置里的 `analytics_url` 用的是 **asyncpg** 驱动（为异步场景准备的），
但我把它直接喂给了同步的 `create_engine()`。
asyncpg **只有异步实现**，SQLAlchemy 必须用 `create_async_engine()` 才配对；
用同步的 `create_engine()` 就会尝试在非 greenlet 上下文里 `await`，直接报 MissingGreenlet。

**关键判断**：这不是"驱动版本问题"，而是**驱动与引擎类型不匹配**。
`postgresql+asyncpg://` 只能配 `create_async_engine`；
`postgresql+psycopg://` 才能配 `create_engine`。

**处置**：
配置层新增 `sync_analytics_ro_url`（`postgresql+psycopg://` + 只读角色），
执行器改用它。同时在原 `analytics_url` 的 docstring 里**显式写明**
"不能配 create_engine()，会报 MissingGreenlet"，避免下次有人再踩。

**规避（强制规则）**：
1. **URL 驱动与引擎类型必须成对**：
   | 驱动标记 | 可用引擎 |
   |---|---|
   | `+asyncpg` / `+aiosqlite` 等 `+a*` | **仅** `create_async_engine` |
   | `+psycopg` / `+psycopg2` | **仅** `create_engine` |
2. 配置里同时提供异步与同步两套 URL 时，**属性名要能自证**：
   `analytics_url`（异步）vs `sync_analytics_ro_url`（同步只读）。
   本项目既有代码其实已有这个约定（`postgres_url` / `sync_postgres_url`），
   我新增时漏了同步版，属于**没有对齐既有约定**。
3. 看到 `MissingGreenlet` 的第一反应是**检查引擎类型**，不要去查连接池或网络。

## L-009 · 截断判定失真：guard 注入 LIMIT N，执行器却想探测 N+1 行

**发生阶段**：P2.2 只读执行器（截断标志测试）

**现象**：
`SELECT * FROM employees`（10000 行）返回 200 行，但 `truncated=False`：
```
assert res.truncated is True
E   assert False is True
```
即**被截断的结果被标成了完整结果**。

**根因**（两层，第二层更隐蔽）：

**第一层：可判定性被自己破坏。**
执行器用"多读一行"判断截断：`fetchmany(max_rows + 1)`，读到 201 行即说明还有更多。
但 guard 在外层注入了 `LIMIT 200`，所以结果**最多只有 200 行**，
`fetchmany(201)` 永远拿不到第 201 行 —— 判定机制从设计上就无法工作。
更糟的是它**不报错**，只是安静地把截断结果标成完整的。

**第二层：警告写在了到不了的分支里。**
`build_observation()` 只在"结果行数 ≤ inline_max_rows"分支里附加截断警告。
但**被截断的结果集必然是大结果集**（200 > 50），一定走另一个分支 ——
所以那句"结果已被截断，不要当成全部"的警告**永远不会被打印**。
这是"逻辑正确但控制流永远到不了"的典型缺陷。

**为什么这两层都很危险**：
它们都属于**静默失真** —— 用户和 LLM 都会把"前 200 行"当成"全部数据"，
于是又回到了本项目一直在消灭的那个问题：**错误但自信**。
只是这次错误来自截断而非检索。

**处置**：
1. guard 注入 `LIMIT (max_rows + 1)` 而非 `max_rows`，让"多读一行"的判定重新成立。
2. 把这个关系写成**显式不变式**并用测试钉死
   （`test_guard_limit_matches_executor_probe`，对 max_rows ∈ {1,50,200,999} 全量校验）；
   因为这类**常量漂移不会报错，只会悄悄给出错误结论**。
3. 截断警告**移出分支**，改为在函数开头统一计算 `truncation_note`，
   两个分支都拼接 —— 消除"控制流到不了"的可能。

**规避（强制规则）**：
1. **凡是"靠多读一行/多查一次来判断边界"的设计，必须回头检查上游有没有把上界卡死。**
   上游的 LIMIT、分页、top_k 都可能让下游的探测逻辑失效。
2. **常量之间的算术关系（A == B + 1）必须写成断言或测试**，
   不能只写在注释里 —— 注释不会在漂移时报警。
3. **警告/兜底逻辑不要放在条件分支深处**，先问一句"触发这个警告的场景，
   会不会恰好走不到这个分支？"。本次就是"被截断 ⇒ 大结果集 ⇒ 走另一个分支"。
4. 返回结果里带"是否完整"这类元信息时，**必须有一条测试专门验证它在
   "确实不完整"时被置位**，否则它可能永远是 False 而无人察觉。

**验证**：修复后 `pytest tests/test_sql_executor_integration.py` → **28 passed**
（含 truncated 置位/不置位、大结果集给概要、截断警告出现在 observation 中）。

## L-010 · 评测指标本身错了：严格相等把 15 个语义正确的答案判成错误

**发生阶段**：P3 Text2SQL 评测（首次跑 Execution Accuracy）

**现象**：
首次评测 EX = **57.14%**，远低于 85% 目标。15 条"结果不符"：

| 问题 | 生成结果 | 期望结果 |
|---|---|---|
| 哪个部门人数最多？ | `('Sales', 1042)` | `('Sales',)` |
| 薪资最高的员工在哪个部门？ | `('Operations', 'Derek', 'Cummings', 179997)` | `('Operations',)` |
| Operations 部门有多少人？ | `('Operations', 972)` | `(972,)` |
| 哪一类费用支出最高？ | `('Office Rent', 13570.9)` | `('Office Rent',)` |

**根因**：
我的 `results_equal()` 用的是**严格相等**（无序时比较排序后的全行）。
但实测发现模型有一个**稳定且合理的倾向**：返回额外的识别性列以增强可读性 ——
问"在哪个部门"它把人也带上，问"多少人"它把部门也带上。
这些答案在语义上**覆盖**了期望结果，且信息更完整，**是更好的答案**。

**关键判据**：15 条里**没有一条**给出了错误的实体或数字 ——
0 条"Sales 写成 Marketing"、0 条"1042 写成别的"。全部只是**列数不同**。

**为什么这个错误很危险**：
一个过严的指标会让人去**"修"本来正确的模型**（比如加 prompt 让它少返回列，
反而降低答案可读性）。**指标错比模型错更难发现**，因为它看起来像"模型不行"。

**处置**：
1. 把比较规则从"严格相等"改为**"期望行必须被生成行覆盖"**：
   长度相等则逐位比较；否则按**子序列**匹配（保持列序）。
2. 保留"生成结果缺列 → 判错"（真错）与"列序颠倒 → 判错"
   （列序颠倒通常意味着选错列，例如 `('Operations','Sales')` vs `('Sales','Operations')`）。
3. 把 15 个被误判的真实案例**固化成回归测试**
   （`TestRealRegressionFromEvaluation`），防止将来有人"修"指标时又判错。

**结果**：EX 从 57.14% → **97.50%**（39/40），Valid SQL Rate 100%，平均生成次数 1.00
（即**一次生成即正确，无需自修正**）。

**规避（强制规则）**：
1. **指标跑出低分时，先看失败样例，再决定是改模型还是改指标。**
   本次若直接去调 prompt"让它少返回几列"，就是把对的改坏。
2. **判断"答案对不对"要看实体与数字，不要只看形状（列数/行数）。**
   人工抽查 5 条失败样例，立刻就能看出全是形状差异而非内容差异。
3. **评测指标必须有单测**（新增 `tests/test_text2sql_metric.py` 38 例）。
   指标是"衡量工具"，工具本身不准，后面所有结论都不可信。
4. 把真实误判案例**固化成回归测试**，比写一段注释有效得多。

## L-011 · 歧义检测过度触发：把"已说清口径"的问题也拦下反问

**发生阶段**：P3 口径澄清机制（与 L-010 同一次评测暴露）

**现象**：
5 条题触发口径澄清，但其中 4 条**不该**触发：
```
❓ 每个部门的平均薪资是多少？     <- 已说"每个部门"，口径明确
❓ 全公司平均薪资是多少？         <- 已说"全公司"，口径明确
❓ Sales 部门的平均薪资是多少？    <- 已说"Sales 部门"，口径明确
❓ 薪资高于全公司平均薪资的人有多少？ <- 同上
```
只有「平均客单价是多少？」是真歧义。

**根因**：
初版把「平均薪资」**一律**当作易歧义指标。但「平均薪资」只有在
**未限定范围**时才有两种解读（按人头平均 vs 各部门平均再平均）；
一旦问题里出现"Sales 部门""全公司""每个部门"，口径就已经唯一确定了。

**为什么比"不澄清"更糟**：
澄清机制的本意是"不猜口径、避免静默错误"。但**过度澄清把本来能答的问题
变成答不了** —— 用户问一个完全清楚的问题却被反问，体验上等同于功能不可用。
安全性机制一旦滥用到伤害可用性，就会被绕过或关闭，最终等于没有。

**处置**：
1. 把「平均薪资」类从"强歧义"降为**条件歧义**：仅在**未出现范围限定词**时才追问。
2. 限定词表**刻意收得很宽**（宁可漏问不要误问）：
   只要出现"部门/团队/岗位/地区"等**分组维度**，或"全公司/所有员工/整体"等
   **整体范围**说法，或"按/分别/每个/口径"等**口径词**，即视为已限定。
3. 补 23 例双向测试（`tests/test_text2sql_ambiguity.py`）：
   **真歧义必须被拦** + **假歧义必须放行**，两个方向都要断言。

**结果**：澄清触发从 5 条 → **1 条**（仅真正的客单价歧义）。

**规避（强制规则）**：
1. **安全/澄清类机制必须做"双向测试"**：
   只测"该拦的拦住了"是不够的，还必须测"不该拦的放行了"。
   单向测试会驱动你把阈值越调越严，最后误伤所有正常输入。
2. **规则类判定的关键词表要按"语义类别"设计，而不是罗列精确短语。**
   初版列了"各部门/每个部门"却没覆盖"Sales 部门"，因为我把注意力放在
   短语变体上，而不是"是否提及分组维度"这个语义上。
3. **每个"拦截/澄清"类规则都要能回答：它的误伤代价是什么？**
   本例误伤代价是"问题答不了"，属于高代价，因此阈值必须保守。

## L-012 · 把"概率性行为"写成"确定性断言" → 必然 flaky

**发生阶段**：P4 运行完整闸口（内嵌 Text2SQL E2E 测试）

**现象**：
闸口 L2 报 1 例失败：
```
FAILED tests/test_text2sql_e2e.py::TestAmbiguityHandling::test_clarified_question_proceeds
1 failed, 414 passed
```
单独重跑 3 次：**通过 / 失败 / 通过** —— 典型的 flaky。

**根因（两层）**：

**第一层：断言本身是概率性的。**
原断言写的是
```python
res = ask(engine, rag_engine, "sales 表里按每笔订单算，平均营收是多少？")
assert res.ok, f"执行失败: {res.answer}"
```
它实际上在断言 **"这次 LLM 一定会生成可执行 SQL"**。
但 LLM 生成有固有随机性（即使 temperature=0），
实测同一问题的成功/反问比例约 **2:1**。
**把概率性行为写成确定性断言，失败是必然的，只是时间问题。**

**第二层（更有价值）：暴露了一个真实的产品缺陷。**
进一步连跑 6 次抓到完整行为分布：
```
run1: clar=True  ok=False   <- 模型调了 ask_clarification 工具
run2: clar=False ok=True    <- 正常执行
run3: clar=True  ok=False   <- 调工具反问
run4: clar=True  ok=False   <- 调工具反问
run5: clar=False ok=False   <- 自由文本反问，但未被识别！
run6: clar=False ok=True
```
`run5` 是关键：**模型不调工具、直接用自由文本列出候选口径反问**，
而我的代码只认 `ask_clarification` 工具调用，
于是同一类行为**时而走 clarify 事件、时而变成"普通答案"** ——
前端呈现与统计口径都不一致。

**处置**：
1. **修产品**：新增 `_looks_like_clarification()` 识别自由文本反问形态
   （疑问语气 + 多个候选项 + 短文本；**保守设计，宁可漏判不误判**），
   让两条路径统一收敛到 `needs_clarification=True`。
2. **修测试**：把概率性断言改为**确定性不变式**断言 ——
   任何一次调用都必须落到三种自洽状态之一：
   ① 成功执行 ② 明确反问 ③ 明确失败并给出说明；
   **禁止第 ④ 种"没执行、没反问、也没说明"的静默状态**。
   这条不变式既稳定，又恰好是本项目核心命题（消灭静默错误）在 Agent 层的对应物。
3. 规则层的确定性行为（`detect_ambiguity`）单独测，不掺 LLM。

**结果**：E2E 连跑 3 次全绿（19 passed × 3），闸口恢复稳定。

**规避（强制规则）**：
1. **断言里不要出现"模型这次一定成功"**。凡是要调 LLM 的测试，
   只能断言**结构不变式**（状态自洽、字段齐全、契约不破），
   不能断言**具体成功率**。成功率属于指标，用评测去统计，不要用单测去卡。
2. **flaky 测试不要靠"重跑两次"掩盖**。先问"它是概率性的吗？"，
   再问"暴露的是测试问题还是产品问题？" —— 本次两层都占，改产品 + 改测试。
3. **把 flaky 现象当成探测器**：本次正是因为追查 flaky，
   才发现了"自由文本反问未被识别"这个真实缺陷。
   如果当时草率地删掉这条测试，缺陷就会留在生产里。
4. **LLM 相关测试要分层**：
   | 层 | 能断言什么 | 速度 |
   |---|---|---|
   | 纯规则（无 LLM） | 具体行为（确定性） | 秒级 |
   | 契约/结构（有 LLM） | 不变式（状态自洽、字段齐全） | 分钟级 |
   | 评测（有 LLM） | 统计指标（EX、成功率） | 分钟级，允许波动 |

## L-013 · 上游偶发 504 无重试 + 错误信息被包装成完全无关的样子

**发生阶段**：P5b 端到端验证 Agent 的 RAG 路径（真连后端容器）

**现象**：
RAG 路径三次请求中一次失败，返回给用户的是：
```
[tool_result] ok=False  知识库检索失败
[delta]       知识库检索失败：generator didn't stop after throw()
```
`generator didn't stop after throw()` 是 **contextlib** 在生成器异常退出时抛的包装异常，
它看起来像"我的生成器/线程池写错了"，把我引向了完全错误的排查方向
（我先去查 `iterate_in_threadpool` 与 Retriever 的生成器交互，浪费了一轮）。

**根因**（看后端日志才找到真凶）：
```
ERROR app.vector.embedding | [Embedding] API 请求失败: 504 Server Error: Gateway Time-out
ERROR app.agent.tools      | [tools] kb_search 失败: generator didn't stop after throw()
```
**上游 embedding 网关偶发 504**，而 `EmbeddingClient.embed()` **没有任何重试**，
一次抖动就直接把整个问答打成失败。真正的 504 藏在异常链的 `__cause__` 里。

**为什么这对 RAG/Agent 类系统特别重要**：
一次问答 = 1 次 embedding + 1 次 rerank + 1~3 次 LLM，Agent 多步链路更长。
若单次外呼成功率 99%，则 5 次外呼的全链路成功率 ≈ 0.99⁵ ≈ **95%** ——
**链路越长，可用性被乘性放大掉的越多**。偶发失败是常态而非异常。

**处置**（两处，缺一不可）：
1. **加重试**：新增 `app/core/retry.py::call_with_retry()`（指数退避 + 抖动），
   接到 embedding（3 次）与 rerank（2 次）。
   策略要点：**只重试瞬时故障**（连接错误/超时/429/5xx）；
   **4xx（除 429）立即抛出** —— 请求本身有问题，重试只浪费配额与时间。
   抖动（jitter）用于避免多个请求同时重试造成"重试风暴"。
2. **修错误信息**：新增 `describe_exception()` 沿 `__cause__`/`__context__`
   解出**根因**并连同异常链一起呈现。修后同样的故障会显示
   `HTTPError: 504 ...（异常链：RuntimeError: generator didn't stop... <- HTTPError: 504）`，
   一眼就能定位。

**规避（强制规则）**：
1. **任何跨进程/跨网络的外呼都必须有重试**，且要区分"瞬时"与"确定性"错误。
   无重试的外呼在长链路里会把可用性乘性拉低。
2. **不能只报最外层异常**。`contextlib`、`asyncio`、线程池、ORM 都可能包装异常，
   让报错信息与真实病因完全无关。
   凡是要把异常暴露给用户或日志的地方，都应**解出异常链的根因**。
3. **看到与自己设计不符的错误信息时，第一反应是去查日志与异常链**，
   而不是相信那句信息 —— 本次若直接去"修线程池"，会白改一通且问题依旧。
4. **端到端验证不可被 hermetic 测试替代**：本次单测全绿（假工具不触发真实外呼），
   只有真连后端容器才暴露出来。这也反证了"三级闸口"里 L3 存在的必要性。

## L-014 · 给工具层加参数后，测试替身没同步签名 → 25 例失败（但这次是好事）

**发生阶段**：P7 RBAC（给 `AgentTools.dispatch` / `sql_answer` 增加 `redact` / `actor`）

**现象**：
完整闸口 L2 报 **25 例失败**，全部是 `TypeError: FakeTools.dispatch() got an unexpected
keyword argument 'redact'`。L3 检索评测**零回归**（证明改动没碰检索链路）。

**根因**：
RBAC 需要把"该身份的敏感列脱敏集合"与"审计标识"从 API 层一直传到 SQL 执行器。
我给真实实现（`AgentTools`）加了参数，但**测试替身（`FakeTools`）没同步签名**，
于是调用点传参时直接 `TypeError`。

**关键判断：这次失败是"好事"**，原因有二：
1. **替身没有用 `**kwargs` 吞掉多余参数**。如果当时图省事写成
   `def dispatch(self, *a, **kw)`，测试会**全部通过**，
   而真实集成里"权限没传下去"就会**静默失效** ——
   用户以为有脱敏，实际看到全部数据。**这是最危险的失败模式：不报错，只是失效。**
2. 三级闸口在**提交前**就拦住了它，而不是等上线后才发现。

**处置**：
1. 同步更新两处测试替身的签名（显式声明 `redact` / `actor`，**不吞 kwargs**）。
2. 新增 `TestPermissionsAreThreaded` 三例，**专门断言权限真的传到了工具层**：
   - RAG 路径：`tools.last_redact == frozenset({"employees.salary"})`
   - SQL 路径：同上
   - 未传权限时必须为 `None`（走零成本快路径，等价于未启用 RBAC）
   假对象记录 `last_redact` / `last_actor` 供断言 —— 这类"参数有没有传下去"
   的缺陷无法靠返回值发现，必须显式观测。

**规避（强制规则）**：
1. **测试替身不要用 `**kwargs` 吞掉未预期的参数**。
   宁可让签名漂移引发 `TypeError`（响亮失败），也不要静默接受
   （安静失效）。**响亮失败 >> 安静失效**。
2. **给跨层接口加参数时，同步检查**：真实实现、所有替身、所有调用点。
   本次漏的是替身，实际只花了 1 轮定位，因为错误信息足够明确。
3. **"参数是否真的传到底"必须单独写测试**。这类缺陷的返回值可能完全正常，
   只有观测中间层（替身记录收到的参数）才能发现。
4. 权限/安全类参数的传递，**要按"会静默失效"来对待**，
   即默认不信任"应该传到了"，而是断言它确实到了。

**验证**：修复后 `check.ps1 -Full` 全绿，**493 passed**；RBAC 端到端实测：
analyst 看到 `179997`、employee 看到 `***`，审计表同时记录两者（角色/行数/脱敏列）。

## L-015 · 修竞态时，必须先写"能复现竞态"的反证测试

**发生阶段**：P7-d 修复会话 `next_seq` 竞态（改造方案「不足」清单 B5）

**背景**：
`SessionService.append` 的写入序列是「SELECT max(seq) → INSERT seq+1」，
典型的 read-modify-write。同一 session 并发追加（双标签页、或 Agent 多步写入）
会算出**同一个 seq**，撞 `unique(session_id, seq)`。

**处置**：改用 PostgreSQL **事务级 advisory lock**（`pg_advisory_xact_lock`），
键为 `hashtext(session_id)`：
- 相比 `SELECT ... FOR UPDATE`：对"尚无消息的新会话"没有行可锁，FOR UPDATE 无效；
- 相比加序列表/DB 序列：**零迁移**，无需回填历史数据；
- `xact` 版本在事务结束时自动释放，**不会泄漏**，无需 try/finally；
- 锁粒度是 session_id ⇒ **不同会话完全并行**，不损吞吐。

**关键做法：先写"反证测试"再写修复。**
`tests/test_session_concurrency.py` 包含两组：

| 测试 | 断言 | 作用 |
|---|---|---|
| `TestRaceExistsWithoutLock` | **不加锁**时并发追加**必须**报唯一约束冲突 | **证明竞态真实存在**，锁不是多余的 |
| `TestLockFixesRace` | 加锁后 8 个并发追加全部成功，且 seq 恰好是 1..8 连续无重复 | 证明修复有效 |

**为什么反证测试不可省**：
如果只写"加锁后成功了"，这个测试在**任何情况下都会通过** ——
包括"我构造的并发根本没触发竞态"以及"锁其实没生效"这两种情况。
换句话说：**没有反证的修复测试，无法区分"修好了"与"没测到"。**
这里的反证测试还顺带验证了并发构造方式确实能压出竞态
（若它哪天不再报冲突，说明测试本身失效了，会立刻被发现）。

**规避（强制规则）**：
1. **修并发/竞态类缺陷时，必须先写一个"能稳定复现该竞态"的测试**，
   确认它在修复前失败、修复后通过。只测"修复后正常"是没有信息量的。
2. 反证测试要**断言具体的失败特征**（这里是唯一约束名 / duplicate），
   而不是笼统的 `assert errors` —— 否则被别的错误"冒名通过"也看不出来。
3. 竞态测试**必须真连数据库**：advisory lock、事务隔离、唯一约束都是
   数据库层语义，用 mock 测等于没测。用 skipif 保护，不拖红无 PG 的环境。
4. 避免用时间阈值断言并发性（易 flaky），改用**行为断言**
   （seq 连续无重复）+ 宽松的耗时上限。

**验证**：`pytest tests/test_session_concurrency.py` → 3 passed；
其中反证测试确认未加锁时确实抛 `uq_messages_session_id_seq` 冲突。
修复后全量 **496 passed**，检索评测零回归。
